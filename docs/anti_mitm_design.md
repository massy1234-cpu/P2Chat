# P2Chat — Server Anti-MITM Design

## Status
- **Phase:** Design / spec for external review
- **Scope:** Active MITM prevention by a malicious server during the first contact and bundle lifecycle.
- **Scale:** Small communities (tens–hundreds of users), possibly self-hosted servers. Members often know each other already.
- **Not covered here:** Symmetric chat encryption (PQXDH + ratchet), network/transport anonymity (Tor). See `docs/recap.md`.

---

## 1. Threat model

We assume a malicious server (or a server compromised by an adversary) that:

- Can observe, replace, or withhold any data it distributes.
- Controls the mapping between usernames and public bundles.
- Does **not** control any client's private keys.

The goal is to make it **impossible for the server to silently substitute a victim's cryptographic identity**, and to make any attempt **provably detectable**.

### The structural limit (must be stated honestly)

If two users have **never** shared any information outside this system (no off-band channel, no common knowledge), and **all** authorities collude, no protocol can create authentication from nothing. This is the same limitation that forces TLS to trust a set of CAs. Every design must therefore pick a minimal "trust anchor" that is not controlled by the server.

In this design the anchor is the **off-band verification (QR / shared secret)** — the single highest-priority layer.

---

## 2. Design principles

1. **Client-side key generation only.** No private key is ever generated by or visible to the server.
2. **Self-certifying identifiers.** The identifier is derived from the identity key, so a bundle "answers" to an ID only if its key hashes to it. The server cannot fabricate a key that matches a victim's ID.
3. **Non-repudiation via client signatures.** Every bundle/operation is signed by the client, so the server cannot invent data attributed to real users.
4. **Off-band anchor first.** Because the community already knows each other, the QR/safety-number exchange is the primary weapon against MITM — not an optional extra.
5. **Per-identity hash-chaining.** Each entry references the previous one, closing replay/rollback without needing a global Merkle tree.
6. **Direct group gossip.** Split-view detection uses direct comparison among group members over an existing channel — no anonymous DHT/Tor gossip needed.

## 4. Protocol layers

### 4.1 Self-certifying identifier

```
ID_user = H(ML-DSA IK public key)     // e.g. 32 bytes, bech32-encoded
```

- The ID is **derived**, never assigned by the server.
- A bundle is accepted for a requested ID only if `H(bundle.IK_mldsa) == ID`.
- Because the hash is one-way, the server **cannot** produce a different key that matches Bob's ID.

### 4.2 Signed hash of the full bundle

Add to `PublicBundle`:

```
BundleHash         = H(canonical_bytes(PublicBundle))
BundleHash_signed  = Sig_MLDSA_IK_priv(BundleHash)
```

- Uses a **deterministic canonical serialization** (e.g. deterministic CBOR per RFC 8949 §4.2, or protobuf with explicit canonicalization rules) so the hash is stable across implementations.
- Any modification to any byte of the bundle invalidates the hash.
- The signed hash proves Bob (the key holder) committed to exactly this bundle.

### 4.3 Client-signed log entries (non-repudiation)

Every operation recorded in the log carries the acting client's signature:

```
LogEntry = { userID, operation, bundleHash, timestamp,
             Sig_client(operation || bundleHash || timestamp) }
```

- Only the holder of Bob's private key can produce a valid signature.
- The server cannot forge an entry **as a real user**.
- The server may only create its **own fake identities** (Sybil), which are limited by registration cost (blind token + PoW) and are not real users with off-band anchors.

### 4.4 Per-identity hash-chaining (anti replay/rollback)

Instead of a global Merkle tree, every identity keeps a **signed chain** where each entry references the previous one:

```
entry_1 = { identityID, seq=1, prev_hash=NULL,   ..., Sig_client }
entry_2 = { identityID, seq=2, prev_hash=H(entry_1), ..., Sig_client }
entry_3 = { identityID, seq=3, prev_hash=H(entry_2), ..., Sig_client }
```

- **Replay:** the server cannot represent an old entry as current — the expected `seq` progression and `prev_hash` link would break.
- **Completeness:** when a client requests "the full history of Bob", the server cannot silently omit an entry — the client detects a hole in the `prev_hash` chain.
- This gives per-identity immutability and ordering with low complexity. A global Merkle tree is not required at this scale.

### 4.5 TOFU + key-change alert (after first contact)

After the first verified contact, the client **pins** the target's key and alerts immediately if it changes:

```
1. store (ID, pinned bundle) after a verified first contact
2. on every subsequent fetch, compare with the pinned key
3. if the key changed → ALERT immediately
   - a change backed by a valid rotation certificate (if master key is used) → "authorized rotation"
   - a change with no valid certificate → "ATTENTION: key changed without authorization"
```

- Covers all conversations after the first contact with no further human effort.
- At first contact, the bundle is validated via the off-band anchor (4.8) plus the per-identity chain (4.4).

### 4.6 Self-monitoring (casual fetch of own bundle)

Periodically, each client:

```
1. request its OWN ID from the server/log
2. verify the returned bundle matches what it actually published
3. verify BundleHash_signed and ID
4. if an unexpected key appears → immediate alert
```

Catches a server that is not serving the correct bundle even to the owner. **Note:** this only protects against a server that lies to the owner; a targeted server shows the owner the truth and lies only to others. It is a guard-rail, not the primary anti-MITM layer.

### 4.7 Direct group gossip (anti split-view)

The remaining attack the above layers cannot block: a server maintaining **two parallel, internally-consistent logs** — a clean one for Alice, a dirty one for Bob.

At this scale, the social graph is already known to all participants, so **anonymous gossip is unnecessary**. Members simply compare the log head over an existing channel (a message in the group, or an informal second channel):

```
compare(my_head, peer_head):
  peer_head is prefix of my_head → peer is behind → OK, no alert
  my_head  is prefix of peer_head → I am behind → update my pin
  neither is a prefix → REAL DIVERGENCE → split-view → public alert
```

- Bidirectional check: only an incompatible history is an alert.
- No DHT, no anonymous peer discovery, no Tor circuits needed for gossip.

### 4.8 Off-band anchor (QR / shared secret) — HIGHEST PRIORITY

- The minimal trust root for the first contact, and the primary weapon at this scale.
- A **QR code** encoding the self-certifying ID (not a human name, to prevent squatting).
- An optional **shared secret / safety number** layer for pairs that already share a channel.
- Members know each other, so a single QR exchange (once per contact) is practical and solves the hardest part of the problem with zero external dependencies.
- After verification, the identity is pinned (4.5); any future key change produces a different ID or an unauthorized change → detected.

## 5. Attack coverage matrix

| Attack | Blocked by |
|---|---|
| Server fabricates Bob's key | 4.1 (self-certifying ID) |
| Server modifies any byte of a bundle | 4.2 (signed bundle hash) |
| Server invents log entries for real users | 4.3 (client signatures) |
| Server replays / rolls back a key | 4.4 (per-identity hash-chain) |
| Server swaps Bob's key after a verified contact | 4.5 (TOFU + key-change alert) |
| Server serves a wrong bundle to its owner | 4.6 (self-monitoring) |
| Server shows two parallel logs (split-view) | 4.7 (direct group gossip) |
| First-contact MITM (the hardest case) | 4.8 (off-band QR) |

## 6. Anonymity layer (separate, orthogonal)

Out of scope for MITM, but referenced: to use the service without the server knowing **who** is active, a **time-limited blind token** (Blind BLS) is used for anonymous access.

```
upload bundle → request anonymous blind token (valid until TOT, then expires)
                → use the service anonymously until TOT
```

- Blind signature makes redemption unlinkable to the issuing session.
- Expiry provides natural rate-limiting.
- Limitations (honest): does not hide the **recipient** (mailbox) or global **volume**; the moment of token request may still be timing-correlated (mitigate with pre-fetch + fresh circuits + randomized delay).

---

## 7. What is NOT solved (honest scope)

- **Key compromise** of a client: if Bob's private key leaks, anything Bob's key signs is trusted. No system resists this.
- **Absolute 100% with zero shared context:** if two users share nothing off-band and all authorities collude, first-contact authentication is impossible. The off-band anchor (4.8) is the required trust root.
- **DoS / censorship:** the server can always withhold data (refuse service). This is not MITM; it is unavoidable.

---

## 8. Recommended implementation order

**Level 1 — indispensable, low effort (do first):**
1. 4.1 — client keys + self-certifying ID
2. 4.2 — bundle signed by the owner
3. 4.8 — off-band QR verification at first contact (**highest priority**)

**Level 2 — very effective, medium effort:**
4. 4.5 — TOFU + automatic key-change alert
5. 4.4 — per-identity hash-chaining
6. 4.7 — direct group gossip

**Level 3 — optional:**
7. 4.6 — self-monitoring
8. (if multi-device) master key + rotation certificates

**If budget is minimal, ship only Levels 1+4.5:** these cover the majority of the real risk with no external dependencies and minimal user effort (a single QR exchange per contact).

---

## 9. Deliberately out of scope (negative cost/benefit at this scale)

- **External independent witnesses / third-party auditing** — designed for millions of unknown users; unnecessary for a closed group whose members know each other.
- **zk state-transition proofs** — large development cost; the off-band anchor (4.8) already covers the same benefit more simply and strongly.
- **TEE / remote attestation** — protects against a hardware-compromised server, which is far less likely than the real threat at this scale.

---

## 10. Open design questions for review

- **Key rotation vs stable ID:** rotating the ML-DSA IK changes the ID. Accept "rotation = new identity", or introduce a stable master key (needed only for multi-device).
- **ID length / encoding:** full 32-byte ID via QR (no truncation to avoid collisions).
- **Deterministic canonical serialization** must be frozen (RFC 8949 §4.2 CBOR or explicit protobuf rules).
- **Gossip frequency:** how often members should compare the log head for a reasonable split-view guarantee.
